Building an AI agent with LangGraph, CrewAI, or LlamaIndex is easy enough on a laptop. Moving that agent to a production AWS environment is where the work appears: orchestration boilerplate, IAM configuration, and infrastructure you now own.

The AWS Bedrock AgentCore CLI is one command-line tool for project scaffolding, a local development server, and AWS deployment, and it stays framework agnostic. You keep the AI framework you already use and get AWS-managed infrastructure for the production side.

## Getting Started (`agentcore create` & `agentcore dev`)

### Installing the CLI

```bash
npm install -g @aws/agentcore
```

Verify the installation:

```bash
agentcore --version
```

### Scaffolding a New Project

The `agentcore create` command launches an interactive wizard that asks for:

- Agent type: Harness (configuration-based) or Agent (code-based)
- Framework: Strands (recommended), LangChain/LangGraph, Google ADK, or OpenAI Agents SDK
- Model provider: Amazon Bedrock, Anthropic, OpenAI, or Google Gemini
- Memory: none, short-term only, or both short-term and long-term
- Build type: CodeZip (default) or Container

For a quick start with recommended defaults:
```bash
agentcore create \
  --name MyAgent \
  --framework Strands \
  --model-provider Bedrock \
  --memory none \
  --build CodeZip
```

This creates a project structure like:
```
MyAgent/
├── agentcore/
│   ├── agentcore.json      # Main configuration
│   ├── aws-targets.json    # Deployment targets (account/region)
│   └── cdk/                # CDK infrastructure (auto-managed)
└── app/
    └── MyAgent/
        ├── main.py         # Agent entrypoint
        ├── pyproject.toml  # Python dependencies
        └── ...
```

### Local Development Workflow

Once the project is scaffolded, start local development with:

```bash
cd MyAgent
agentcore dev
```

This command creates a Python virtual environment, installs the dependencies, and starts a local development server with hot reload. It opens the agent inspector in your browser on port 8080 by default and reloads when you change code.

Useful development flags include:
- `--no-browser`: Use terminal-based TUI instead of browser inspector
- `--no-traces`: Disable trace writing to `agentcore/.cli/traces`
- `--logs`: Tail server logs in non-interactive mode
- `--port <N>`: Specify custom development ports

## Deploying to AWS (`agentcore deploy` & `agentcore invoke`)

### Deployment Process

When ready to deploy to AWS, run:

```bash
agentcore deploy
```

The deployment packages your code into a zip artifact, or builds a container if you passed `--build Container`. It then uses AWS CDK to synthesize and provision the required resources, creates an AgentCore Runtime endpoint for the agent, and configures CloudWatch logging and observability.

The first deployment is slow because CDK has to bootstrap. Later deployments are much faster, since the infrastructure is already there.

You can preview changes before deploying:
```bash
agentcore deploy --dry-run
```

Check deployment status at any time:
```bash
agentcore status
```

### Invoking Deployed Agents

Once deployed, interact with your agent using:

```bash
agentcore invoke --prompt "Hello, what can you do?"
```

For agents configured with payment capabilities (using the x402 standard):
```bash
agentcore invoke \
  --prompt "Access https://example-x402-merchant.com/paid-api" \
  --payment-instrument-id <INSTRUMENT_ID> \
  --auto-session \
  --payment-user-id user@example.com
```

## Managing Enterprise Guardrails & Resources

The `agentcore add` command adds capabilities to an existing agent:

```bash
# Add memory capabilities
agentcore add memory

# Add additional agents to your project
agentcore add agent

# Connect external APIs/tools via Gateway
agentcore add gateway

# Add API keys for non-Bedrock providers
agentcore add credential

# Add quality evaluation components
agentcore add evaluator

# Add payment capabilities (x402)
agentcore add payment-manager
agentcore add payment-connector
```

After adding capabilities, deploy your changes:
```bash
agentcore deploy
```

### Understanding agentcore.json

`agentcore/agentcore.json` holds the agent's configuration. Here is an example for a Strands-based agent with a Bedrock model and a gateway tool:

```json
{
  "schema_version": "2024-01-01",
  "agents": {
    "my-agent": {
      "type": "agent",
      "framework": {
        "type": "strands",
        "agent": "MyAgent"
      },
      "model": {
        "provider": "bedrock",
        "model_id": "anthropic.claude-3-sonnet-20240229-v1:0",
        "region": "us-east-1",
        "temperature": 0.7,
        "max_tokens": 4096
      },
      "system_prompt": "You are a helpful assistant that can answer questions and help with tasks.",
      "memory": {
        "short_term": {
          "max_turns": 10
        }
      },
      "tools": [
        {
          "type": "gateway",
          "gateway_id": "my-api-gateway"
        }
      ],
      "credential_references": [
        {
          "credential_id": "openai-api-key",
          "usage": "llm_provider"
        }
      ]
    }
  }
}
```

## Key Capabilities Explained

### AgentCore Memory

Short-term memory keeps conversation context for the immediate interaction. Long-term memory uses vector storage (Qdrant or similar) for knowledge that has to persist. Summarization thresholds and embedding models are configurable.

### AgentCore Gateway

Gateway connects the agent to external services. It handles authentication for API keys, OAuth, and AWS IAM roles behind one interface, transforms requests and responses with JMESPath or JavaScript, applies rate limits and quota protection, and emits logs, metrics, and traces. It also integrates MCP servers for tool discovery and execution.

### AgentCore Observability

Observability covers distributed tracing of the agent's reasoning steps, tool invocation tracking with performance metrics, and CloudWatch integration for centralized logging and monitoring. You can add custom metrics for business-specific KPIs.

## What the CLI Actually Buys You

The AgentCore CLI closes the gap between local prototyping and a production AWS deployment. It handles the infrastructure wiring while leaving the framework choice open, which lets engineers:

- Focus on agent logic rather than orchestration boilerplate
- Move from local development to AWS deployment without rewriting the agent
- Inherit AWS-managed identity, observability, and scaling rather than building them
- Keep the freedom to use Strands, LangGraph, or another framework
